# 本地代码审计模型调优过程

本文记录 `devstral-small-2-review-tuned` 从可运行基线到当前版本的完整调优过程、遇到的问题、修复方式和仍然存在的限制。

## 1. 最终目标

目标不是让模型输出更多，而是让它成为一个可高频使用、可重复验证的代码审计模型：

- 尽量提高 P0/P1 真实问题召回率；
- 每条发现都能定位到文件、行号和代码证据；
- 降低风格建议、无依据边界和重复汇总造成的误报；
- API 错误、空响应和输出截断必须明确失败；
- 适用于多个 Git 仓库，并且真实业务数据不进入公共仓库。

## 2. 初始状态

最初的本地模型是 `devstral-small-2-review`，后来已有一个 `devstral-small-2-review` 的 Ollama 派生模型。检查其 Modelfile 后确认：

- `temperature=0.15`；
- `num_ctx=32768`；
- 没有专门的代码审计系统规则和人工确认示例；
- 全局 `local-review.sh` 主要把 Git diff 和审查要求拼接成一次普通请求。

因此没有直接做 LoRA 微调，而是先优化输入、系统指令、示例、运行边界和评测方式。原始模型没有被覆盖。

## 3. 调优过程与遇到的问题

### 3.1 把稳定规则从普通提示词提升为系统指令

原脚本把审查规则放在 diff 后面，规则和待审查内容处在同一个用户输入中。改为通过 Ollama `/api/generate` 的 `system` 字段发送稳定规则，用户输入只承载仓库状态、规则文件、示例和 diff。

同时增加：

- `--context <file>`，允许显式加入相关接口、调用方、DTO、测试等上下文；
- `--examples <file>` 和 `LOCAL_REVIEW_EXAMPLES_FILE`，支持本机私有 few-shot 示例；
- `temperature`、`seed`、`num_ctx`、`num_predict`、`keep_alive` 的环境变量覆盖。

### 3.2 建立派生模型

创建了 `devstral-small-2-review-tuned:latest`，基础模型仍然是本地已有的 `devstral-small-2-review:latest`。当前 Modelfile 参数为：

```text
num_ctx 16384
temperature 0
seed 42
top_k 40
top_p 0.9
num_predict 4096
```

派生模型增加了证据驱动的代码审计系统规则，但没有重新下载或训练基础权重。

### 3.3 发现并修复脚本可用性问题

第一次端到端测试时，在没有传 `--context` 的情况下，Bash 严格模式因为空数组展开直接退出：

```text
context_files[@]: unbound variable
```

修复为只有在上下文数组非空时才遍历。这个问题说明高可用性必须用真实命令链路验证，而不能只做 `bash -n`。

### 3.4 抑制低价值误报

初始测试中模型正确发现了除零和空值风险，但还报告了：

- `final` 类可能影响未来扩展；
- 缺少 Javadoc；
- 没有足够证据的泛化可维护性问题。

随后加入规则：除非项目规则或当前差异证明了具体行为、兼容性、安全或维护风险，否则不报告风格、命名、Javadoc、`final` 或泛化建议。

### 3.5 发现无限输出导致的长时间请求

在加入 few-shot 示例后，一次小 diff 审查曾经超过 5 分钟没有返回。原因不是请求没有发出，而是没有设置最大生成长度，模型持续生成过多解释。

修复方式：

- 设置 `num_predict=4096`；
- 检查 Ollama 返回的 `done_reason`；
- 如果返回 `length`，命令以非零状态失败，并明确提示“模型输出被截断”；
- 不把半截审计结果伪装成成功结果；
- 关闭长时间自动重试，避免单次故障拖延几十分钟。

### 3.6 修正 Java 整数除法语义

模型一度错误地把普通 Java 整数除法报告为“可能溢出”，并声称 `Integer.MIN_VALUE / -1` 会抛出 `ArithmeticException`。

加入 Java 语义约束和负例后，当前规则明确：

- 关注包装类型为 `null`；
- 关注除数为 `0`；
- `int` 的 `Integer.MIN_VALUE / -1` 不应被描述为会抛出 `ArithmeticException`；
- 不把同一根因的具体问题再次汇总成重复问题。

在固定临时路径的一轮合成测试中，模型曾只保留两个有证据的问题：`Integer` 空值和除零。但随后把同一夹具复制到不同临时仓库并重复调用时，模型又生成了整数除法截断、`final`、Javadoc 和重复汇总等误报，因此这次结果不能作为稳定性验收。

### 3.7 发现采样和服务稳定性问题

重复测试发现固定 `seed` 并不能保证这个本地模型在不同请求中完全一致：

- `top_k=1` 会让完整审计请求长时间无响应；改回 `top_k=40`、`top_p=0.9` 后，短审计请求可在约 20 秒返回；
- 同一差异有时返回 2 条 P1，有时返回 5 条（额外包含 P2/P3 误报）；
- 只看退出码不足以验收，因此 `evals/run-synthetic.sh` 现在严格检查正例必须恰好 2 条、负例不能有任何 P0～P3，并单独检查截断故障；
- 连续测试可临时使用 `OLLAMA_REVIEW_KEEP_ALIVE=5m`，但这只减少模型反复加载，不能替代稳定性验证。

后续针对真实的“预签名票据完成/取消后仍可重放”问题做了脱敏留出测试：通用命令的 `top_k=40/top_p=0.9` 连续 5 次只命中 3 次，而 `top_k=1/top_p=1` 连续 5 次全部命中同一条 P1。但在真实配置小 diff 上，贪心采样曾超过两分钟仍未返回。综合召回、响应时间和高可用性，个人 wrapper 与通用命令都保留 `top_k=40/top_p=0.9` 默认值；贪心参数仅作为高影响安全差异的可选覆盖。该选择不增加模型或服务组件，只改变解码策略。

同时修复了大提交的分片边界：以前单个 unified-diff hunk 超过预算会直接失败；现在仅在确实超过预算时按原始行顺序拆成多个窗口，并重复文件/hunk 头保留路径和行坐标。无法拆分的超长单行仍会明确失败，不会静默丢弃差异内容。

真实全量审查还发现分片模型会把未展示的方法误认为“代码被截断”或缺少校验。系统指令现明确声明分片外内容未知，禁止据此生成问题；只有当前窗口可见证据或确定性预检才能成立。这样不会为了减少误报而合并、隐藏真实 finding。

分片回归还使用了 180 行无风险 Java 大 hunk（预算 2500 字节）：修复后完整拆分并返回 clean，未触发“无法拆分”或“代码不完整”误报。

性能审计发现两处纯启动开销：模型探测原先每次轮询固定睡眠 1 秒，且自动选中模型后又重复探测；现改为 100ms 轮询并复用成功探测结果。Java 构建预检也改为一次建立源码索引后复用，避免每个 import 重扫全仓库；这些改动不改变超时、证据范围或分片串行策略。

在最新规则下又重跑了两个真实 `platform-api` 留出提交：`91bff253`（HR 客户端凭据校验，62 秒）和 `2f6c3934`（数据库模式变更，118 秒）均完成且只返回 clean；结果保存在本机私有评测目录，不进入公开仓库。

因此原始长规则和高温度配置未达到阶段 0 回归门槛；后续在 3.8 中通过精简规则和低温度修复了这组公开合成样例。

### 3.8 通过合成回归门槛

将系统指令压缩为短规则、加入 `int a + b` 的明确负例、移除重复注入的私有示例，并把默认温度改为 `0` 后，重新运行严格门禁：

- 除法、URL 凭证泄漏和租户隔离正例共 4 个已知根因，5/5 次均全部命中，输出哈希一致；
- 三组 clean 负例（整数加法、内部 token header、租户约束完整查询）5/5 次均只输出“未发现阻塞问题”，输出哈希一致；
- `num_predict=1` 的截断故障路径以非零状态退出并提示截断；
- 默认上下文从 32k 调整为 16k，避免当前机器在完整审计请求上长时间无响应。

阶段 0 现在通过，但这只是合成回归门槛；真实历史提交评测仍未完成。

历史提交运行器已用一个本地 `platform-api` 提交试跑。模型这次返回了若干文件和行号，但缺少要求的 P0～P3/信息严重级别，并混入测试缺口建议；新的结构门禁正确以非零状态拒绝，并保留原始输出供人工复核，这类结果不能计入召回率。

### 3.9 为大差异增加确定性分片

真实提交试跑还暴露了一个与 RAG 无关的工程问题：一个只有约 6 KB、但包含多个文件的提交仍可能让单次生成达到长度上限。于是 `local-review` 增加了按 `diff --git` 文件边界、再按 unified diff hunk 边界分片的回退链路：差异超过 3000 字节时，每个分片单独请求模型，结果按分片顺序拼接，不做去重或摘要；任何一个分片超时、截断或缺少严重级别/位置，整次审查都失败，并把已经完成的分片仅以诊断形式展示。无法进一步拆分的单个超大 hunk 会明确失败。

分片不是 RAG：没有向量库、Embedding 或相似度召回，项目规则和显式上下文仍由提示词传入。分片请求会加载本机私有 few-shot 示例，以抑制已经确认的接口契约误报；同时只展示当前分片的文件列表，避免模型根据全局 Git 状态跨分片编造问题。可以通过 `OLLAMA_REVIEW_CHUNK_TIMEOUT_SECONDS`、`OLLAMA_REVIEW_CHUNK_NUM_PREDICT` 和 `OLLAMA_REVIEW_MAX_DIFF_BYTES` 调整。

当前分片预算按 UTF-8 字节计算并固定 `LC_ALL=C`；先按文件，再按 hunk 打包。单个 hunk 仍大于预算时会显式失败，不会把超预算内容偷偷发送给模型。`diff --cc`/combined diff 也会明确拒绝，因为它需要先恢复合并冲突语义，不能按普通单文件 diff 猜测。

这里的字节预算只计算 Git diff；`AGENTS.md`、显式 `--context`、README 和 system prompt 仍会额外占用上下文。因此该门禁不能替代 `num_ctx` 容量检查，项目上下文较大时要提高 `OLLAMA_REVIEW_NUM_CTX` 或拆分输入。

在验证过程中，`platform-api` 的测试文件分片曾在 Ollama 中长时间无响应；设置分片独立超时后，命令会在 60/180 秒边界明确失败，而不是无限等待。一次模型被 Ctrl-C 中断后还曾长期显示 `Stopping...`，停止该 Ollama 模型后合成回归恢复。这些服务层故障不会被计入模型召回率。

在当前规则和路径/格式门禁下，`91bff253`、`2f6c3934` 的首轮输出分别包含 5、12 条泛化误报；加入证据自检和私有接口/租户负例后，`cbe47ea0`、`501ad5a1`、`ccea445b`、`a1284658`、`f1a093a3` 均完整返回 clean，耗时约 10～54 秒。`39955c8` 默认预算会显式拒绝超大 hunk，提高预算后耗时 342 秒且产生 29 条误报。这说明提示隔离和负例能改善已知误报簇，但阶段 1 仍必须逐条人工标注，不能把 clean 结果直接当作召回率证明。

针对 `420ae70c` 暴露的漏报，命令增加了确定性 Java import 预检：只提取当前差异新增/修改的 import，并按同仓库源码索引检查类型是否存在；预检证据按分片隔离后再交给模型。该机制已在该提交快照上识别出 5 个缺失 DTO 的 P1 构建阻断，但外部依赖、生成源码和跨模块类型仍需结合构建上下文人工确认，不能把路径启发式直接当作完整编译器。

独立验证也在 `420ae70c` 的临时 worktree 执行了 `mvn -DskipTests compile`：Maven 编译失败，并列出五个 `Directory*DTO` 缺失符号，与预检结果一致。

后续合成回归发现本地模型偶尔会在有效问题清单末尾追加“未发现阻塞问题”。运行器现在只删除这一条独立矛盾标记，不改写或隐藏任何问题段；同时模型规则明确要求最终输出在 clean 标记和问题清单之间二选一。修复后 5/5 正例、5/5 clean 负例和截断故障门禁均通过，五次重复输出哈希保持稳定。

尝试加入“凭证从 URL 查询参数读取并转发”的安全正例时，模型最初在 180 秒上限内未返回。增加针对性正/负 few-shot，并明确 JDK 标准库依赖不应被猜测为构建问题后，该样本已稳定返回一个凭证泄漏问题；header 传递对照样本返回 clean，现已纳入默认合成门禁。

随后加入租户隔离正/负样本：查询只使用资源 ID 时稳定命中跨租户读取风险；查询同时使用 `tenantId` 和资源 ID 时，经过参数 null/信息级误报边界规则收紧后稳定返回 clean。默认 5 次回归现在覆盖 4 个真实根因、3 个 clean 负例和截断故障路径，输出哈希在每个样例内一致。

个人高性能 profile 的 `keep_alive=5m` 不是盲目增加参数：在同一台 Mac、同一个 clean fixture 上，连续两次耗时约为 23s/4s；每次设置 `keep_alive=0` 则约为 20s/21s。它只改善连续审查的第二次加载时间；用户更在意电量时可以覆盖为 `0`。个人 wrapper 和通用 `local-review` 默认都保持 `top_k=40/top_p=0.9`；对已确认的高影响安全差异，可单次覆盖为 `top_k=1/top_p=1`，但应接受更长响应时间风险。

最新个人 profile 的 precision 回归也重新验证了旧误报簇：`91bff253`、`2f6c3934` 和 `39955c85` 在当前私有示例与证据规则下均返回 clean；同时 `420ae70c` 的缺失类型预检和带 `platform-file` context 的 `f6fc2f89` 仍命中真实 P1 根因（同一删除类型根因可能展开为多个受影响引用）。随后用同步后的 tuned 模型复测 `cbe47ea0`（过滤分片不完整误报后 227 秒 clean）、`501ad5a1`（30 秒 clean）和 `ccea445b`（272 秒 clean）。旧的 20 提交 scorecard 没有被直接改写，避免把不同参数阶段的结果混在一起。

针对 `a1284658` 暴露的误报，个人规则补充了 Java `instanceof` 模式匹配的 null 语义、Spring 拦截器异常透传契约，以及 POM/Gradle optional/provided 和 `@ConditionalOnClass` 的外部依赖边界；同时按问题首行合并模型在代码块周围插入的续行，仅用于格式校验，不改写最终输出。复测结果：`a1284658` 返回 clean，`420ae70c` 仍命中 5 个缺失 DTO 的 P1，带显式 context 的 `f6fc2f89` 仍命中跨仓库删除类型 P1；合成回归一轮全部通过。

`2fa4cf1` 首次复测曾因把已有默认值和集中式 `Duration` 边界校验误判为多个问题而输出截断；补充“默认值 + helper 已覆盖 null/非正值/溢出/上限”的边界规则后，同一提交在当前个人 profile 下 35 秒返回 clean。该规则不豁免 helper 未覆盖的具体非法值，也没有提高预测长度。

随后用当前个人 profile 单独复测 `420ae70c33916523afd4f4c6dc21fd6cc5095da0`：耗时 242 秒，返回 5 个缺失 `Directory*DTO` 的 P1 编译阻断，退出码为 0，未出现截断或 clean 标记矛盾。该结果与独立 Maven 编译失败证据一致；耗时偏高来自完整提交快照的分片串行审查，因此没有用提高并发或无限延长超时来掩盖成本。

最新一轮留出回归再次复测历史误报簇：`91bff253`（24 秒）、`2f6c3934`（11 秒）和 `39955c85`（23 秒）均返回 clean；同一轮中的 `de408cc`、`acc6212`、`10b1af3`、`cd11118` 也均返回 clean。此前验证的 `420ae70c` 缺失类型 P1 和带 context 的 `f6fc2f89` 删除类型 P1 仍保持命中。结果只用于精度回归，不代表已有足够样本宣称生产级召回率。

随后复测了 5 个不同功能簇：`501ad5a1`（22 秒）、`ccea445b`（27 秒）、`f1a093a3`（5 秒）、`e4888c70`（8 秒）和 `b4ea10f`（15 秒）均返回 clean。至此当前 profile 已对 14 个真实提交做过精度回归；其中只有经过人工确认的 P1 根因才计入召回率，clean 结果不等价于业务正确性证明。

在完整 5 轮合成回归中，4 个问题/安全/租户正例和 3 个 clean 负例均为 5/5 通过，所有重复运行哈希一致；截断故障路径也按预期以非零状态失败。期间发现模型偶尔在问题清单后追加带句号的 clean 标记，运行器现仅移除该独立标记行，不改写或隐藏任何问题段。

为扩大留出覆盖，又复测早期 API/依赖变更 `029e6ff`（21 秒）、`47d7761`（4 秒）和 `1621d8e`（5 秒），以及清单中更早的 `89ea7d8`（34 秒）、`12a1aeb`（26 秒）和 `6dc87ec`（12 秒），均返回 clean。当前个人 profile 已覆盖评测清单的全部 20 个真实提交；其中 18 个为人工确认的 clean 回归样本，2 个为人工确认的 P1 召回样本，仍不足以代表完整生产分布。

跨仓库泛化试跑选取 `platform-file` 的 `7b62671` 临时文件清理和 `2e33eaf` 凭证配置变更；前者在补充后台任务/limit 语义边界后由 4 条误报变为 49 秒 clean，后者 6 秒 clean。随后合成回归一轮再次通过，说明规则没有削弱租户与凭证泄漏正例；跨仓库结果暂不并入 `platform-api` 的 20 提交分数。

维护任务 clean 夹具已加入公开合成回归，覆盖“忽略租户上下文枚举、逐条按租户回收、limit 夹紧”语义。加入后完整 5 轮结果为：正例 20/20、clean 负例 20/20，所有哈希一致，截断故障门禁通过。

## 6. Codex 接入过程中遇到的问题

调优期间也验证了 Codex 与 Ollama 的两种接入方式，这些问题影响的是接入稳定性，不是基础模型权重：

- 直接使用 Codex OSS/Ollama 路径时，模型列表刷新曾因为客户端期待的响应字段与 Ollama 兼容接口返回的 OpenAI 风格列表结构不一致而报错；这不应通过反复下载模型来解决。
- `devstral-small-2` 不支持 thinking。Codex 默认推理强度会触发重连，改为 `model_reasoning_effort="none"` 后，profile 调用成功返回。
- `codex exec review --commit <sha>` 不接受额外的普通提示词参数。提交审查应按该子命令的参数约定调用，避免把 CLI 用法错误误判成模型故障。

最终保留两条互补链路：Codex profile 用于交互式探索，`local-review` 用于可复现的批量审计、输出完整性检查和跨仓库使用。两条链路共享同一个 Ollama 派生模型，但不把交互式成功误认为审计质量已经经过量化验证。

## 7. 当前限制与下一阶段

当前仍然没有完成真正的 20～30 个历史提交评测，因此还不能声称已经达到 90% 的 P0/P1 召回率目标。下一阶段应：

1. 从真实项目挑选至少 20 个历史提交；
2. 人工确认每个提交的真实问题、误报和无问题结果；
3. 按提交切分 few-shot 示例和留出评测集；
4. 记录召回率、误报率、行号准确率、输出完整性和耗时；
5. 只有 Prompt、上下文和 few-shot 仍然不足时，才评估 LoRA/QLoRA。

未经人工确认的模型输出不能直接作为训练标签，业务源码和真实 diff 不能提交到这个公开仓库。
